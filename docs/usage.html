GroveFS 平台客户端 · 使用说明

本页讲两个平台壳怎么用：grovefs-mac（macOS 经 macFUSE，同一份源码在 Linux 上用纯 Rust 挂载，可直接当端到端探针）与 grovefs-win（Windows 经 WinFsp，把视图挂成盘符）。它们不是另一套存储：走的是与 grovefs mount 完全相同的帧协议、相同的 meta-server（权威树）与 data-server（对象字节）；换的只是内核桥——不依赖 Linux FUSE，也不走 NFS。

win/ = WinFsp 2.1 + MSVC 或 LLVM-MinGW mac/ = macFUSE 4.x（Linux 上纯 Rust 挂载） 依赖图只有客户端那一半：无 rusqlite / postgres / tokio 协议无版本号：兼容与否取决于 M_OPEN 握手解析的宽严 本页断言数字取自 2026-11-21 实跑

约定：下文 $C 指本仓根目录（grovefs-client/），$G 指内核仓的 grovefs 可执行文件，$K 指本仓客户端二进制（$C/target/release/grovefs-mac，或预编译的 $C/dist/grovefs-mac）。示例地址统一用虚构内网 10.0.0.1，元数据服务端口 50110、数据服务端口 50100；照抄时换成自己的。窄屏（手机）阅读时，宽表格与命令块都可以左右滑动。

第一部分 · 起步

1.1 两个壳与内核的关系

一次挂载始终需要两个服务端坐标：权威树在 meta-server，文件字节在 data-server。内核自带客户端 grovefs mount 面向 Linux FUSE；本仓把同一套客户端骨架搬到另外两个内核桥上，因此它们与内核客户端读写同一棵树、同一批字节，可以互为验证（内核段回归里就有一条"内核挂载读回客户端写入的字节"）。

成员内核桥Cargo feature 组合复用了内核的什么产物
win/ WinFsp 签名驱动 → 盘符 remote-only（不带 fuser/libc） 只要传输缝：RemoteMeta + RemoteBackend + proto 帧。WinFsp 回调面自己实现 grovefs-win.exe
mac/ macFUSE → 目录（挂载点） remote-only,fuse-bridge 连 fs_impl::GroveFS 那套 FUSE 实现一起复用——与 grovefs mount 同一条挂载路径，只换宿主桥 grovefs-mac

两个 crate 都是纯客户端：服务端/控制面子树（本地引擎、meta-server、MCP、apikeys、pg_store）在 native 门后，不进依赖图。这条边界是可验的，不是口头承诺：

# mac 壳（Linux 与 macOS 都能跑这条）
$C && cargo tree -p grovefs-mac | grep -cE 'rusqlite|libsqlite3|postgres|tokio'
# 0

# win 壳：按 Windows 目标三元组数一遍，连 fuser 也应为 0
cd win && cargo tree --target x86_64-pc-windows-gnu \
  | grep -cE 'rusqlite|libsqlite3|postgres|tokio|fuser'
# 0
这条 grep 是已知的回归高发点：once 有 optional 依赖的调用泄漏进被客户端复用的模块，默认（全 feature）构建毫无感觉，remote-only 这条腿直接断链。改到 grovefs/src/remote/ 或 platform.rs 时，务必按 4.4 的两条最窄 feature 门各建一次。

1.2 五分钟跑通

示例环境：存储机 10.0.0.1 上已起 meta-server（50110）与 data-server（50100），存储根 /data/gfs，已建基视图 alice，集群带静态令牌 s3cr3t；同一台存储机还起了 grovefs manager serve（50055，join/roster key 已分发到客户机），本页挂载示例优先用它引导。客户机是一台 macOS（或一台只想快速验证协议、不想装 FUSE 的 Linux）。服务端怎么起来归内核文档管，本页只给挂载侧。 
# macOS：挂载到一个【已存在】的目录（macFUSE 不会替你建目录）
sudo mkdir -p /Volumes/alice
# 首选：让 manager 用签名 roster 供两个坐标（§2.1）
$C/dist/grovefs-mac --manager 10.0.0.1:50055 --roster-key-file /etc/grovefs/roster.key \
                    --view alice --token s3cr3t --mount /Volumes/alice
# 坐标只能由 manager 的签名 roster 提供；无 manager 不会回退到手抄地址
# grovefs-mac: mounted view 'alice' at /Volumes/alice (read-only: false, content read-only: false) — press Ctrl-C to unmount

# 另一个终端：写一笔，然后确认字节落在存储机上而不是本机
mkdir /Volumes/alice/docs && echo hi > /Volumes/alice/docs/a.txt
cat /Volumes/alice/docs/a.txt
# hi
ssh 10.0.0.1 'ls /data/gfs/blocks | head'      # 看得到 00 01 02 … 的哈希桶目录

# 收工：Ctrl-C（走 session 的 unmounter，不留死卷）
# Windows（PowerShell，已装 WinFsp 2.1）：挂成盘符，或交给 WinFsp 挑空盘
.\grovefs-win.exe --manager 10.0.0.1:50055 --roster-key-file C:\etc\grovefs\roster.key `
                  --view alice --token s3cr3t --mount M:
# 坐标只能由 manager 的签名 roster 提供；无 manager 不会回退到手抄地址
# grovefs-win: mounted view 'alice' at M: (read-only: false, content read-only: false) — press Ctrl-C to unmount
两行的判据相同：挂载横幅里的两个布尔值就是这个挂载的合同。read-only 来自 M_OPEN ack 字节 [0]（派生透镜或只读 key）或你自己的 --ro；content read-only 来自字节 [2]（fork）。看到 content read-only: true 却还能改文件内容，是客户端版本落后（见 4.2）。

1.3 dist/ 预编译与版本核对

dist/ 是入库的发布面，让没有 Rust 工具链的机器也能试客户端。它有两个坑，先说清：

文件它是什么它不是什么
dist/grovefs-macLinux x86_64 上构建的 mac 壳。fuser 在这条路上用纯 Rust 挂载，所以这个二进制在 Linux 上就能真挂出一个 GroveFS 视图；同一份源码在 macOS 上对着 macFUSE 4.x 构建即可不是 macOS 上的安装产物（要真在 Mac 上用，自己 cargo build -p grovefs-mac --release）
dist/grovefs-win同一个 crate 在 Linux 上的 cfg(not(windows)) 分叉：能解析 CLI，然后打印"只能在 Windows 上跑"就退出不是 Windows 可执行文件，也不含 WinFsp FFI。真正的 grovefs-win.exe 必须在 Windows 上用 WinFsp 2.1 + MSVC/LLVM-MinGW 构建
# 拿到 dist 先做两件事：校验完整性、看清它是哪棵源码树
cd $C/dist && sha256sum -c SHA256SUMS.txt
# grovefs-mac: 成功
# grovefs-win: 成功

cat BUILDINFO.txt | head -12      # 客户端提交 ↔ 内核提交 ↔ rustc ↔ 构建日期

BUILDINFO.txt 里那对提交坐标是唯一有效的版本答案：帧协议不带版本号（见 5.1），"我的客户端能不能配你的服务端"只能靠它 + 一次真挂载来回答。当前这批预编译产物的客户端与内核提交坐标、构建工具链和校验值，以 BUILDINFO.txt 与 SHA256SUMS.txt 为准；它包含带 manager 挂载引导（--manager）的客户端实现，并沿用 Data-Access Capability 握手。

不要在正在使用的挂载上换 dist/ 二进制：一个二进制一个 inode，覆盖写会让活挂载的页缓存读回 ETXTBSY 类脏值。换二进制前先 grep grovefs /proc/mounts 看清有没有挂着的卷，卸掉再换；跨 inode 的 cp truncate 覆盖同样是这个雷。

1.4 服务端前置条件

客户端只是第三个进程，它不会替你建树、也不会替你起服务。挂载前，服务端侧必须已经：

需要由谁提供缺了会怎样（客户端会看到）
视图已显式创建grovefs view --meta-dir … create --view alice按 explicit-view 文案拒绝：view … does not exist；M_OPEN 从不替客户端偷偷建一棵树
两个服务在听meta-server --listen + data-server --listencannot reach meta-server …: Connection refused，退出非零
凭据服务端 --token / --require-api-key / --data-access-key 三选一或叠加三道门各自的拒因原文会透传到客户端 stderr（见 3.1）

客户端与服务端必须来自同一代握手。服务端升级加了 M_OPEN 字段时，旧客户端不是"少显示点信息"，而是可能把该只读的东西挂成可写——这就是本页反复出现的那条边界。

1.5 自己构建

macOS 客户端

# 前置：macFUSE 4.x（内核扩展要在系统设置里放行）+ pkgconf，fuser 的 build.rs 会去探测它
brew install --cask macfuse
brew install pkgconf
cd $C && cargo build -p grovefs-mac --release
# 产物：$C/target/release/grovefs-mac

Apple Silicon 上第一次挂载前，需在系统设置 → 隐私与安全性里允许第三方内核扩展。只想在 Linux 上做端到端验证则不需要任何东西：cargo build -p grovefs-mac 出来的二进制用 fuser 的纯 Rust 挂载就能挂（dist/ 里那枚正是这么来的）。

Windows 客户端

  1. 装 WinFsp 2.1（提供 winfsp-x64.dll）与 WinFsp SDK / developer files（import library + 头文件，bindgen 需要基于 windows.h 的 include 路径）。
  2. 装 libclang（winfsp-sys 跑 bindgen；找不到时设 LIBCLANG_PATH）。
  3. 用受支持的工具链：MSVC（推荐：VS Build Tools 的"使用 C++ 的桌面开发" + Windows SDK，rustup default stable-msvc）或 LLVM-MinGW（build.rs 会为 gnu/llvm ABI 发出对应的 delayload 链接参数）。纯 GNU/MinGW-w64 gcc 不支持。
# 从 win/ 里构建，或在工作区根加 -p grovefs-win
cd $C/win
cargo build --release --target x86_64-pc-windows-msvc
# 产物落在工作区 target/x86_64-pc-windows-msvc/release/grovefs-win.exe

build.rs 是自包含的：它把 delay-load 指令（MSVC 走 /DELAYLOAD:winfsp-x64.dll，LLVM-MinGW 走 -Wl,--delayload=…）直接内联，而不是在构建期依赖 winfsp crate，所以这个 build script 在非 Windows 主机上也能编译。delay-load 的附带好处：链接期不需要 WinFsp 的 import library，DLL 在首次调用时从 WinFsp 安装位置解析。

没有 Windows、也没有 libclang 时怎么验证 cfg(windows) 代码

fs.rs 与 main.rs 的挂载分支被 #[cfg(windows)] 门住，Linux 主机默认根本不编译它们。仓里带一个纯 Rust 的 WinFsp API 镜像 stub（win/vendor/winfsp-api-mirror，签名逐字抄自 winfsp-0.13.2+winfsp-2.1），用 [patch.crates-io] 换上它，就能让那段代码进入类型检查：

# 在【工作区根】$C/Cargo.toml 临时加（注意：加在成员 win/Cargo.toml 里会被 cargo 忽略并警告）
#   [patch.crates-io]
#   winfsp = { path = "win/vendor/winfsp-api-mirror" }
cd $C && cargo check -p grovefs-win --target x86_64-pc-windows-gnu
# ⚠ 检查完必须还原：stub 没有 FFI，链接出来的二进制无法服务 IRP。
#   patch 会改动 Cargo.lock，收尾用 git checkout -- Cargo.lock 复原。
这一步确实抓到过两个真机构建同样会撞的编译错误（DirInfo::<255>::new() 的 const 泛型不参与推断；host.mount(MountPoint::NextFreeDrive) 要按值传，双重引用会被 HRTB 拒）。它验证不到的只有与真 crate 的 ABI 链接——那仍然需要上面那套真实 Windows 构建。

第二部分 · 挂载与参数

2.1 参数总表

两个壳共享同一组「连哪儿、连谁、用什么凭据」的参数；差异只在挂载点形态与缓存控制——缓存那一层 WinFsp 与 fuser/macFUSE 的表达方式不同，所以 win 侧没有那几个 flag。表以 --help 为准（本仓自己的 dist/ 里那两枚二进制就能打印出来）。

参数winmac含义
--manager HOST:PORT必填必填挂载唯一引导入口：向这台 grovefs manager 要部署的签名 roster，从中解析元数据与数据服务坐标。手写的 --meta-addr/--data-addr 已从两个客户端移除，传入会得到 clap 未知参数错误；env GROVEFS_MANAGER。只问一次，之后 manager 死活与这个挂载无关
--roster-key-file PATH必填必填验签 roster 的 HMAC 密钥（64 个 hex 字符）。给的是文件不是值：密钥是对称的，落在 argv 里就进了 ps 与 shell history。env GROVEFS_ROSTER_KEY_FILE
--deployment NAME可选可选--manager 要解析哪个部署，默认 default（即 manager define 不给 --name 时用的那个名字）。env GROVEFS_DEPLOYMENT
--view NAME必填必填要呈现的视图名。名字必须先存在（基视图，或有定义的派生/别名/fork）
--mount TARGET必填必填win：盘符 M:、目录路径，或 next（让 WinFsp 挑第一个空盘）；mac：已存在的目录
--token TOKEN可选可选集群静态令牌，对应服务端 --token。空 = 只按无凭据尝试
--api-key ID:SECRET可选可选面向 --require-api-key 服务端的可撤销按调用方凭据（grovefs apikey create --for mount 铸造）。旗标留空时回退 env GROVEFS_API_KEY——与 grovefs mount 同一入口形状，部署可以把 secret 留在 ps 与 shell history 之外
--ro可选可选无论服务端允许什么都强制只读。与服务端下发的只读是「或」关系
--no-cache—可选严格跨客户端一致性：dentry/attr TTL 归零 + FOPEN_DIRECT_IO，绕过内核缓存直读
--cache-ttl SECS—可选内核属性/目录项缓存 TTL，默认 2 秒；给了 --no-cache 就被忽略
--layout FILE—可选本挂载专属的显示透镜（与内核 mount --layout 同一规则文件、同一 LayoutMeta）：hide/only/map/link 只重组这一个挂载看到的目录形，存储树与其他客户端不受影响；经透镜写落到真实条目，往透镜合成的目录里直接新建报 EPERM。win 壳暂缺：映射层用的是 WinFsp 的 \path\to\name 分解，透镜的路径空间与之不同，需真机验证后再接
-o, --options …—可选透传给 fuser/macFUSE：allow_root、allow_other、default_permissions、auto_unmount、volname=…、ro

两个壳都没有 Data-Access Capability 相关的 flag：那是握手自己带的（见 3.1），运维不需要也没有手填的入口。

manager 是唯一坐标来源

两个客户端不再提供 --meta-addr 或 --data-addr。挂载必须经 --manager（或 GROVEFS_MANAGER）取得部署的签名 roster，再由 --roster-key-file（或 GROVEFS_ROSTER_KEY_FILE）验签；缺少 manager 或验签密钥时直接拒挂，不会回退到手写地址。解析成功后第一件事是打一行横幅，把拿到的两个坐标原样报出来，运维不用猜：

$C/dist/grovefs-mac --manager 10.0.0.5:50055 --roster-key-file /etc/grovefs/roster.key \
                    --view alice --token s3cr3t --mount /Volumes/alice
grovefs-mac: bootstrapped from manager 10.0.0.5:50055: deployment 'default' meta [10.0.0.1:50110] data [10.0.0.1:50100] (roster epoch 3, expires 1795263816)
grovefs-mac: mounted view 'alice' at /Volumes/alice (read-only: false, content read-only: false) — press Ctrl-C to unmount
manager 是引导，不是代理，也不是依赖：它在挂载建立的那一刻被问一次，之后它的重启与宕机都动不到这个活挂载，只能拒绝一次新挂载（fail-closed）。所以「客户端要不要常年能连到 manager」这个问题的答案是不要。
roster 里 data 列了多个成员时，客户端拒挂，原文是 roster for deployment '…' declares 2 data servers: this client does not stripe, so it cannot mount this deployment — use the kernel grovefs mount, which takes the whole list (…)。这不是漏功能而是刻意的：条带住在 backend::sharded，它是 native 门内的东西，remote-only 构建链不上（4.3）。同一份 roster 给内核 grovefs mount 是能挂的——这条不对称由内核板子 client 段 H 分成对钉住。

2.2 grovefs-mac 挂载

grovefs-mac --manager HOST:PORT --roster-key-file F --view NAME \
            [--deployment NAME] [--token TOKEN] [--api-key ID:SECRET] --mount DIR \
            [--ro] [--no-cache] [--cache-ttl SECS] [--layout FILE] [-o OPT]...
  • 挂载点必须已存在：macFUSE 往上挂，不替你建目录。习惯做法是 /Volumes/alice，并且 mac 侧默认会带上 volname=GroveFS-<view>，让访达显示成有名字的卷。
  • 卸载只用 Ctrl-C：信号处理里调 session 自带的 unmounter，正常收工会打印 grovefs-mac: unmounted <目录> 并且不留死卷。硬 kill -9 之后要用 fusermount -u 兜底。
  • 挂载横幅是合同：mounted view 'x' at /y (read-only: R, content read-only: C)。R 由 ack 字节 [0] 或 --ro/-o ro 决定，C 由字节 [2]（fork）决定；名字解到别的视图时，在此之前还会先打一行合同说明（见 3.2）。
  • macOS 与 Linux 同一份源码：在 Linux 上它用 fuser 的纯 Rust 挂载，因此可以当作「非内核客户端」的协议探针来跑真挂载——内核板子的 client 段正是这么用的。

2.3 grovefs-win 挂载

grovefs-win --manager HOST:PORT --roster-key-file F --view NAME \
            [--deployment NAME] [--token TOKEN] [--api-key ID:SECRET] \
            --mount M:|next|DIR [--ro]
  • 盘符 / next / 目录三选一。next 让 WinFsp 选第一个空闲盘符，脚本里比硬编码 M: 稳。
  • 卷参数是写死的一套（VolumeParams）：文件系统名 GroveFs、扇区 4096、名字长度 255、case_preserved_names(true) + case_sensitive_search(false)（保大小写显示、查找不区分，即 NTFS 的习惯），persistent_acls / reparse_points / named_streams 均关。
  • 整卷只读在挂载期决定：read_only = --ro || 服务端 ack 字节 [0]，命中时以 read_only_volume(true) 交给 WinFsp，整个卷在 IFS 层就是只读的。注意 fork 的内容只读不在这个旗里——它是运行期逐 IRP 判的，所以 fork 卷看起来是可写盘、但写文件内容会撞 STATUS_MEDIA_WRITE_PROTECTED。
  • 内容只读是运行期逐个 IRP 判的：fork 的 write 与 set_file_size 返回 STATUS_MEDIA_WRITE_PROTECTED，而 mkdir/rename/unlink/chmod 照常放行——判定集中在 win/src/mapping.rs 的一个函数里（见 3.3）。
  • 凭据形态：安全边界是服务端那道门；文件只上报「存在 + 只读位」，没有 NT ACL（4.3）。
  • 在 Linux 上跑 dist/grovefs-win 只会看到：grovefs-win: grovefs-win mounts via WinFsp and only runs on Windows (parsed: …; to test on this host run `cargo test`)。这不是失败，是 cfg(not(windows)) 分叉的正常行为。

2.4 缓存与多客户端一致性

这里的缓存是客户端主机内核里的属性/目录项缓存，不是服务端的什么开关。默认 --cache-ttl 2：同一挂载点上的名字解析与 stat 结果最多复用 2 秒，也就是说另一个客户端造成的结构变化，本机最多滞后约 2 秒看到；要「对面一写、这边立刻可见」就挂 --no-cache，代价是每个 open 都带 FOPEN_DIRECT_IO，读直穿到 data-server。win 侧没这两个 flag，缓存时效由 WinFsp 的 volume/dir/file info 超时（本页 2.3 那组卷参数）决。

fork 挂载不协商 writeback cache。这是刻意的：内容写必须真的走到挂载这一层才能被拒——如果内核把写攒在页缓存里延迟回写，应用会「写成功、事后悄悄丢字节」，那比 EROFS 难查得多。所以 content_ro 为真时，客户端不参与 writeback 协商，第一次 write(2) 就返回 EROFS。mac 侧这条由复用的 fs_impl::GroveFS 保证，win 侧由 mapping.rs 的同一判定保证。

第三部分 · 权限与视图语义

3.1 三道门：token / api-key / Data-Access Capability

三道门都在服务端把关，客户端只负责「把凭据带上」和「把拒因原样显示出来」。它们可以叠加，叠加时是 AND。

门服务端开关客户端要做什么拒挂时客户端打印
集群静态令牌 meta-server --token / data-server --token 带 --token，两个平面都要对得上 meta-server rejected the access token
可撤销按调用方凭据 --require-api-key（key 库在服务端的 meta/api_keys.db） 带 --api-key ID:SECRET（apikey create --for mount 铸，scope 必须是 mount 或 any） no api key presented: … / authentication failed: unknown api key id / … invalid api key secret / scope 不符时点名两个 scope
Data-Access Capability（数据面准入） meta-server --data-access-key HEX 与同一把 data-server --data-access-key HEX 不需要任何 flag：meta 在 M_OPEN 确认包尾部签发能力，客户端 latch 住，之后每个数据面 OP_OPEN 自动重放（RemoteBackend::new_with_dac） grovefs-mac: data-server requires a Data-Access Capability minted by this cluster's meta-server (start that meta-server with the same --data-access-key, and mount against it)

第三道门要解决的是「伪冒的 meta-server 把合法 data-server 当免费磁盘」：只带 --token 时，任何一个知道令牌的元数据服务都能指挥客户端往诚实的 data-server 上读写。能力是 meta 用它与 data 之间共享的 HMAC 密钥现签的「我确实批准过这次挂载」凭据，data 独立验签；伪冒的 meta 签不出来，它的客户端就在第一个 OP_OPEN 被拒。它是准入证明，不是按视图的数据 ACL（数据键空间仍是一平面 KV）。

对客户端运维只有两条实际后果：(1) 客户端不需要配密钥，也没有地方配；(2) 客户端必须与服务端同代——一个还不认识 M_OPEN 尾部字段的旧二进制，在这种部署上会挂不上，并打印上面那句服务端原话。「挂不上 + 这句原话」= 版本落后，不是集群坏了，也不是可以绕过去的告警。

3.2 四种视图在客户端的表现

视图名先由 M_OPEN 解析成真实形态，确认包里带回三个尾部字段（解析后的名字、基视图名、种类）加上能力。客户端据此决定怎么挂，并把合同打进横幅。

基视图 baseview create自己拥有整树可写（无额外行）

基视图不会被 fork 的操作波及：fork 里改名、删名字只动它自己那棵结构树，共享字节仍被账本记着（这也是删 fork 不会误伤基视图数据的原因）。反过来，基视图上覆盖写内容，fork 读到的是同一批新字节——它们本来就是同一份内容。

3.3 客户端是内容只读的唯一执行点

这是本页最需要被记住的一条。服务端不 gate 数据字节流：data-server 只认对象 key，它不知道也不关心这个 key 属于哪个视图、是不是 fork 共享的。于是「fork 的内容不许改」这条约定，唯一的执行位置就是挂载本身——mac 侧交给复用的 fs_impl::GroveFS（与 grovefs mount 同一条路径），win 侧集中在一个纯函数里：

# win/src/mapping.rs —— 两个标志、一类操作，一个判定点（可在任意主机上单测）
pub enum Mutation { Content, Tree }

pub fn refuse_mutation(read_only: bool, content_ro: bool, m: Mutation) -> Option<i32> {
    match m {
        Mutation::Tree if read_only => Some(STATUS_MEDIA_WRITE_PROTECTED),
        Mutation::Content if read_only || content_ro => Some(STATUS_MEDIA_WRITE_PROTECTED),
        _ => None,
    }
}

读法：整卷只读拒一切改动；内容只读只拒内容改动（write、截断/改长度）。树操作（建目录、改名、删名、chmod）在 fork 上放行。mac 侧的规则形状一样，只是由 fs_impl 里的 readonly / content_ro 两参数承担。

推论：握手每长一个字段，两个壳都要跟着改，否则不是「显示少一点信息」而是「把该拒的写放过去」。这就是 5.1 那条纪律存在的原因，也是内核板子必须拿发布二进制（而不是内核自己的客户端）去挂真服务端的理由。

4.2 静默降级的识别

协议不带版本号，所以「客户端比服务端旧」不一定报错。会报错的那一半是好的（DAC 就是这一类：直接拒挂并说原话）；不会报错的那一半才是风险：

症状成因怎么定性
fork 视图挂上后，改文件内容竟然成功，而且基视图里同一个文件跟着变了 客户端不认识 M_OPEN ack 字节 [2]，把 fork 当普通视图挂；而服务端不 gate 字节流，没人拦这笔写 看挂载横幅：没有 content read-only 这一项，或 fork 该为 true 却报了 false → 二进制版本落后，立即重编/换 dist
派生透镜挂出来可写 同上形状：字节 [0] 没被读，或读了没参与挂载决策 横幅应为 read-only: true，且额外有一行 derived view … read-only lens
挂载横幅里没有别名/派生/fork 那行合同说明，但读写都正常 只是缺定义尾（旧客户端停在字节 [2] 就不往下解），或这个视图本就是基视图 基视图本来就没那行；其他三种名字缺少该行才是版本信号。这一条是纯观感问题，不像上两行那样危险 
# 不抱假设地问一句：这个二进制到底会不会解析 M_OPEN 的定义尾？
# release 且 strip 过的二进制里，错误文案仍在，可以当版本指纹用：
grep -c "view-definition tail" $C/dist/grovefs-mac
# 1  = 当代（会读定义尾，也就带 DAC 重放）
# 0  = pre-DAC，在 --data-access-key 集群上会拒挂，在 fork 上会把内容挂成可写
为什么不拿时戳或文件名当版本判据：因为 dist/ 会被重打，一个名字叫「旧版」的文件可能已经是新版。做负对照（验“旧客户端真的被拒”）时尤其重要：必须当场用内容探针确认它真的是旧的，否则那条断言会静默退化成恒真。

4.3 v1 边界（不支持项）

项现状为什么
数据面条带（多 data-server）只接受 manager roster 解析出的一个 data 成员；roster 若列了多个 data 成员，直接拒挂而不是挑一个条带在 backend::sharded，它是 native 门内的东西，remote-only 构建链不上它；替客户端选成员等于给它一个与部署声明不同的布局
roster 的后续刷新只在挂载建立那一刻问一次；之后 manager 改了声明，活挂载不会跟着换坐标刻意设计：manager 是引导不是代理，所以它的宕机只会拒绝一次新挂载（fail-closed），动不到已建立的挂载。要换坐标就重挂；内核 mount --manager 同形
按用户/按视图的数据 ACL无。getuid() 只作为审计归属发给 meta访问控权靠 --token / --api-key（可附只读位）/ DAC；数据键空间是一平面 KV
win：POSIX 记录锁不透过挂载暴露GroveFS 有原语，到 WinFsp 字节范围锁的映射是未做的后续工作
win：NT ACL / 符号链 reparse point / 备用数据流无。文件只报「存在 + 只读位」；符号链节点能表示但不渲染成 reparse point与上一行同属 WinFsp 回调面的未完成部分（卷参数里也直接关掉了）
mac：多线程分发单线程 session loopfuser 的 n_threads/clone_fd 是 Linux 优化；macFUSE 就服一个环
mac：tags / resource fork / ACL无不造 macOS 专有元数据，树就是 GroveFS 视图，按 POSIX 形状呈现

4.4 改动后怎么验证

四层，从上到下代价递增；前三层在任意 Linux 主机上都能跑，不需要 Mac 或 Windows。

① 本地（本仓，无需任何服务端）

要验 #[cfg(windows)] 那段挂载代码，走 1.5 最后的 vendor stub 路线（patch 只加在工作区根，验完连 Cargo.lock 一起复原）。

② 两条最窄 feature 门（在内核仓里跑）

这一段回答的问题别的套件都回答不了：板子其余部分只跑内核自己的客户端 CLI，一个只对外部客户端生效的握手回归会一路绿灯过。A–H 八段共 54 条断言（带负对照 55）：SQLite / PG 两档控制面（含内核挂载读回客户端字节、同一棵树两个客户端）、未知视图拒挂、token 门两边、DAC 能力走通 M_OPEN → OP_OPEN（同 store 再起一对无 DAC 的服务验旧路径逐字节不变）、fork 结构可写而 write(2) 撞 EROFS 且基视图仍可写、派生透镜整卷只读、--require-api-key 认 --api-key，以及 H 段的 manager 引导 16 条：只给 --manager 就挂得上（命令行里没有任何存储节点地址）、横幅报出解析到的两个坐标、字节落在 roster 指的那台 data-server，五种拒因（与显式坐标冲突、缺 --roster-key-file、错 key、key 文件形态不对、manager 连不上）各自点名，env 兜底两个变量也能挂，最后一对是不对称的钉：2 成员条带 roster 这里拒 does not stripe，而同一份 roster 内核挂载能挂上。

# 脚本在内核仓的 .build-bin/（被 /.*/ 排除，随检出走、不随 clone 走）
cd ../grovefs
PRE_DAC_REV=<一个 dist/ 还早于 DAC 握手的 grovefs-client 提交> \
  bash .build-bin/test_client.sh
# ==================== SUMMARY: pass=55 fail=0 ====================
# 不带 PRE_DAC_REV 会自己跳过那条负对照：pass=54 fail=0
# $GROVEFS_CLIENT / $CLIENT_BIN 可改仓位置与所用二进制（默认 ../grovefs-client/dist/grovefs-mac）
# dist 若早于 --manager，H 段整段打印 SKIPPED 而不拉低 GREEN（跨版本配对是默认行为）
负对照那一条的代价最高：它把「新客户端能挂上」与「旧客户端真的被拒」成对钉住——只前一半的话，只能证明集群默认不设防。所以它的判据写成了内容探针（4.2）：拿到的二进制若已会解析定义尾，该条直接报红而不是默默跳过。

④ 真平台冒烟

Windows 上只能真机：WinFsp 2.1 环境里挂盘符，至少跑一遍 mkdir / 写读 / 改名 / 删，并在 fork 视图上确认 write 与改长度都返回写保护。macOS 上同理验 macFUSE 那条桥（dist/ 里那个二进制替不了它，见 1.3）。

附 · 对齐纪律与文档指针

5.1 与内核对齐的纪律

帧协议没有版本号：兼容性取决于两端对 M_OPEN 握手解析的宽严。两条规则由此而来，两个壳都按它实现：

  • 服务端发的每个字段都要读。M_OPEN ack 字节 [0] = 只读视图（派生透镜，或只读 API key），字节 [1] = 可分页 readdir，字节 [2] = fork（结构可写、内容 EROFS）；尾部字段依次为解析后的视图名、基视图名、种类、Data-Access Capability。忽略字节 [2] 不是观感问题：内容门住在挂载里，服务端从不 gate 字节流。
  • meta 平面交给 data 平面的东西，要原样重放。meta-server --data-access-key 在 M_OPEN 现签的能力，两个壳都通过 RemoteBackend::new_with_dac 逐次带给 data-server 验签。
采用新握手字段或客户端 CLI 的改动，必须同时重打 dist/。否则「零工具链试客户端」的入口会继续踩刚修完的那个坑。每批 dist/ 都要：换两枚二进制（release + strip）、重算 SHA256SUMS.txt、改写 BUILDINFO.txt 的双仓坐标；收尾跑一次 sha256sum -c。本批的实际坐标以 BUILDINFO.txt 为准。

反向的约束也存在：内核仓文档（docs/docs.html 的断言明细表与回归那一段正文）里复述的 client 段断言条数，以它自己的板实跑为源，由内核仓的文档对账脚本兼管——改了本层行为、动了 A–H 任何一段的断言数，就要在内核仓同步那两处。
